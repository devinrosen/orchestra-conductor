# Agent Team Usage Review — 2026-02-15

Analysis of how `/implement-features` uses agent teams, compared against best practices from `docs/AGENT-TEAMS.md`.

## What We're Doing Right

- **Worktree isolation** — each teammate gets its own directory, avoiding file conflicts (a top best practice)
- **Focused spawn prompts** — planners and implementers get specific, scoped instructions
- **Shutting down agents promptly** — the skill shuts down planners immediately after PLAN.md is confirmed
- **Fast-track mode** — avoids spinning up two agents for trivial work

## What's Wrong / Misaligned with Best Practices

### 1. Two agents per feature is expensive and often unnecessary

The research says agent teams use **~7x more tokens** than standard sessions. Our workflow spawns a **planner** then an **implementer** per feature — that's 2 full context windows per feature. For a 3-feature session, that's 6 teammates + the lead = 7 agents.

The AGENT-TEAMS doc says: "Keep teams small — token usage is roughly proportional to team size." Fast-track mode already proves that a single agent can plan + implement small tasks. This could extend to medium (M-scope) tasks too — there's no fundamental reason a single agent can't write PLAN.md, get it approved, and then implement.

**Suggestion**: Default to single-agent-per-feature (plan → approval pause → implement) and only split into separate planner/implementer for L-scope work where the plan might be rejected.

### 2. Planners don't need to be teammates — subagents would work

The AGENT-TEAMS doc draws a clear distinction: use **subagents** when you need focused workers that report back, use **agent teams** when teammates need to communicate with each other. Planners never message each other — they each independently research and write PLAN.md. They're a textbook subagent use case.

Using `Task` tool subagents for planning would be cheaper (results summarized back, no full teammate context) and simpler (no need to create a team, manage shutdown, etc.).

**Suggestion**: Use subagents for planning, only create a team for the implementation phase (if even needed — see point 1).

### 3. The lead does too little during planning, too much during wrap-up

The lead sits idle while planners work, then does a heavy wrap-up: reading postmortems, pushing branches, creating PRs, writing the lead postmortem, updating ACTIONS.md. The research doc says "Monitor and steer" — but the lead can't steer because it's just waiting for completion messages.

Meanwhile, the PR creation, branch pushing, and cleanup could be done by the implementer before it finishes (or by a subagent).

### 4. Postmortems add significant token cost for marginal value

Every agent writes a postmortem, then the lead reads all of them and writes its own, then `/review-postmortems` reads them all again. That's 3 passes over the same information. Each postmortem adds to the agent's context (the prompt instructions alone are ~15 lines per agent).

The AGENT-TEAMS doc says "Keep spawn prompts focused — everything in the prompt adds to context from the start." Postmortem instructions add non-trivial weight to every spawn prompt.

**Suggestion**: Have agents report findings in their completion message instead of writing a separate file. The lead can write a single session postmortem that captures everything.

### 5. The SKILL.md is extremely long (~190 lines) and loaded into every session

The implement-features skill is essentially a mini-manual with a growing "Lessons Learned" section (30+ items). This entire document gets loaded into the lead's context at the start. Many lessons are now baked into the instructions themselves (e.g., "never use plan mode" appears in both the instructions AND lessons learned).

**Suggestion**: Prune Lessons Learned — graduate items into the instructions and remove them from the list. Keep the skill under 100 lines.

### 6. No use of Sonnet for teammates

The research doc explicitly recommends: "Use Sonnet for teammates — balances capability and cost for coordination tasks." Spawn prompts don't specify a model, so teammates inherit Opus. Planners and implementers following a structured plan don't need Opus-level reasoning — Sonnet would work and cost significantly less.

**Suggestion**: Specify `model: "sonnet"` when spawning teammates.

## Token Reduction Summary

| Change | Estimated Savings |
|--------|------------------|
| Single agent per feature (not planner + implementer) | ~50% fewer agents |
| Subagents for planning instead of teammates | Lower per-agent cost |
| Sonnet for teammates | ~5x cheaper per agent |
| Trim postmortem overhead | Shorter prompts + fewer files |
| Prune SKILL.md length | Smaller lead context |

The biggest wins are (1) fewer agents and (2) using Sonnet. Combined, those could cut token usage by 5-10x for a typical session.

### 7. settings.local.json has cruft

The permissions list has leaked bash commands (a full commit message as a permission entry, hardcoded temp paths, exploratory find commands). Not a token issue but messy and could cause confusing permission behavior.
